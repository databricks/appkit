# refactor: Generate plugin types from JSON Schema

## Overview

Eliminate three hand-maintained copies of `ResourceFieldEntry`, `ResourceRequirement`, and `PluginManifest` by generating TypeScript interfaces from `plugin-manifest.schema.json` using `json-schema-to-typescript`. The existing custom script (`tools/generate-registry-types.ts`) stays for runtime values only (enum, constants).

## Problem Statement

The same interfaces are manually maintained in three places:

1. **`packages/shared/src/plugin.ts`** — uses `string` for `type`/`permission` (loose)
2. **`packages/appkit/src/registry/types.ts`** — uses `ResourceType` enum / `ResourcePermission` union (strict)
3. **`packages/shared/src/cli/commands/plugin/manifest-types.ts`** — lightweight copy for CLI

When the schema changes (e.g., new resource type, new field), all three must be updated manually. They already diverge — `appkit` includes `onSetupMessage` while `registry/types.ts` does not.

## Proposed Solution

**Hybrid approach** (see brainstorm: `docs/brainstorms/2026-03-12-generate-types-from-schema-brainstorm.md`):

| What | How |
|---|---|
| Interfaces (`ResourceFieldEntry`, `ResourceRequirement`, `PluginManifest`) | Generated by `json-schema-to-typescript` into `packages/shared` |
| `ResourceType` enum (runtime) | Custom script (slimmed down) |
| `PERMISSION_HIERARCHY_BY_TYPE`, `PERMISSIONS_BY_TYPE` (runtime) | Custom script (slimmed down) |
| Permission type aliases (`SecretPermission`, etc.) | Custom script (kept — library may not emit them reliably from `allOf`/`if`/`then`) |
| `ResourceEntry`, `ValidationResult` | Hand-written in `appkit/registry/types.ts` (extends generated base) |
| `TemplatePlugin`, `TemplatePluginsManifest` | Hand-written in `manifest-types.ts` (references generated `PluginManifest`) |

## Technical Considerations

### Critical: `allOf`/`if`/`then` handling

The schema uses conditional validation (`allOf` with `if`/`then`) to narrow `permission` per resource type. `json-schema-to-typescript` has inconsistent support for this pattern:

- **`permission` field** will likely generate as `string` (the base type), not the narrowed union
- **Per-type permission aliases** (`SecretPermission`, `JobPermission`, etc.) may not be emitted since they're only referenced inside conditional branches

**Mitigation:** Keep the custom script generating `ResourcePermission` union and per-type aliases. The generated `ResourceRequirement.permission` field will be `string` from the library, overridden to `ResourcePermission` in the appkit wrapper type.

### `fields` optionality mismatch

Schema declares `fields` as optional (not in `required` array), but all existing code treats it as required. The resource registry accesses `entry.fields` directly in 9+ locations.

**Mitigation:** The appkit wrapper type makes `fields` required:
```typescript
// In appkit/registry/types.ts
import type { ResourceRequirement as GeneratedResourceRequirement } from "shared";

export interface ResourceRequirement extends GeneratedResourceRequirement {
  type: ResourceType;                    // Narrow from string to enum
  permission: ResourcePermission;        // Narrow from string to union
  fields: Record<string, ResourceFieldEntry>;  // Make required
}
```

### `config.schema` type divergence

Schema defines a restrictive subset of JSON Schema. The codebase uses the full `JSONSchema7` type. Generated `ConfigSchema` would reject valid JSON Schema constructs.

**Mitigation:** Keep `config.schema` typed as `JSONSchema7` in the hand-written `PluginManifest` wrapper. Do not expose the generated `ConfigSchema` in the plugin-facing API.

### `ResourceType` — enum vs string union

`json-schema-to-typescript` will generate `type` as a string union (`"secret" | "job" | ...`). The codebase uses `ResourceType.SECRET` (enum member access) in 9+ files.

**Mitigation:** The custom script continues generating the `ResourceType` enum. String union from generated type is assignable to enum values. The appkit wrapper narrows `type` to `ResourceType`.

### Build pipeline

Currently generation runs in `appkit`'s `build:package`. With generated types in `shared`, generation must run during `shared`'s build (which executes first via turbo dependency ordering).

**Plan:** Two generation steps:
- `shared/build:package`: `json-schema-to-typescript` → `plugin-manifest.generated.ts`
- `appkit/build:package`: custom script → `types.generated.ts` (enum + constants only)

## Implementation Phases

### Phase 0: Spike (validate approach)

Run `json-schema-to-typescript` against the actual schema and inspect output. Verify:

- [x] What `permission` resolves to in `ResourceRequirement` (`string` vs union)
- [x] Whether `$defs` types (`SecretPermission`, `ResourceFieldEntry`, etc.) are emitted
- [x] Whether `fields` is optional in generated output
- [x] What `configSchema`/`configSchemaProperty` look like
- [x] Whether `ResourceType` generates as a string union from `$ref`

**File:** Create a throwaway script `tools/spike-schema-types.ts` that calls `compileFromFile()` and prints the output. Delete after validation.

**Key `json-schema-to-typescript` options to test:**
```typescript
{
  bannerComment: "// AUTO-GENERATED from plugin-manifest.schema.json\n// Do not edit.",
  additionalProperties: false,
  strictIndexSignatures: true,
  unreachableDefinitions: true,  // Emit all $defs even if not referenced from root
  style: { semi: true, singleQuote: false },
}
```

**Exit criteria:** We know exactly which types are usable as-is and which need wrapper overrides.
